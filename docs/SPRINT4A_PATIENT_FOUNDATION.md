# Sprint 4A — Patient Foundation

## Objective

Move from independent report workspaces to patient-scoped workspaces. This is the prerequisite for longitudinal comparison, chat, and RAG; no later component may retrieve data across patient IDs.

## Delivered in this slice

- `patients` collection and API (`POST /api/v1/patients`, `GET /api/v1/patients`, `GET /api/v1/patients/{patient_id}`).
- Patient profile IDs generated by the backend, rather than user-entered IDs.
- Analysis workspace creation validates a supplied patient ID.
- `GET /api/v1/analysis/sessions?patient_id=...` returns only that patient's workspaces.
- Frontend profile creation and patient selection; upload is disabled until a patient is selected.

## Longitudinal comparison slice

- `HistoryService` retrieves prior parsed workspaces only for the selected `patient_id`.
- `ComparisonService` compares only same-name, same-unit numeric lab facts and records the prior/current value, report-provided status, numeric direction, and a factual finding status (`NEW_ABNORMAL`, `PERSISTENT_IMPROVING`, `PERSISTENT_WORSENING`, `PERSISTENT_STABLE`, or `RESOLVED`).
- `comparison_context` is persisted with the analysis and passed into LangGraph, so summary and risk outputs can reference prior data without querying across patients.
- The comparison catalogue is versioned and currently normalizes a limited set of stable test-label aliases and units. It has no clinical ranges, critical values, or unit-conversion rules until these are clinician reviewed.
- Result contract: `GET /api/v1/analysis/{analysis_id}/result`.
- Timeline contract: `GET /api/v1/patients/{patient_id}/timeline`.

## Results and timeline UI

- The selected-patient timeline displays chronological workspaces and available comparison facts.
- Each parsed workspace has a **Result** action that retrieves and displays current findings, longitudinal comparison, risk/consultation data, and the validated summary.
- The UI renders backend facts only and labels the result as non-diagnostic.

## Next slices

1. Add more comparison test cases and clinician-reviewed comparability/unit-conversion rules.
2. Build the timeline/result frontend views against the stable API contracts.
3. Add patient-scoped conversational retrieval and RAG.

## Boundary

This slice deliberately does not add login/accounts: there is no authentication layer yet. Once authentication is introduced, profiles will be owned by `user_id`; all patient reads will then additionally filter by that owner.
